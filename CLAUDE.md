# tinyworlds

Miniature, explorable pixel-art cities. Each **world** is one city redrawn as an isometric
pixel-art map, generated procedurally from open data and served as a pannable, zoomable tile
map under its own path:

| World     | City                                 | Notes                                                        |
| --------- | ------------------------------------ | ------------------------------------------------------------ |
| `tinynyc` | New York City, the five boroughs     | surveyed building heights, street-tree census, ferries       |
| `tinyrao` | Ribeirão Preto, São Paulo, Brazil    | heights estimated from a satellite raster, cane fields around |
| `tinyorl` | Orlando, Florida (the built-up area) | downtown, the lakes, the airport and theme-park country      |
| `tinyfte` | El Calafate, Patagonia, Argentina    | the town on Lago Argentino and the steppe; heights from the raster |
| `tinyvlc` | Valencia, Spain                      | old town, Turia gardens, City of Arts and Sciences, port and beaches |
| `tinylas` | Las Vegas, Nevada                    | the Strip, downtown, the airport and the desert valley       |
| `tinylax` | Los Angeles, California (the basin)  | downtown, Hollywood and its sign, the beaches, the stadiums, LAX; County community lines |
| `tinywinterfell`, `tinykingslanding` | imagined places | no map data: generated by code from scratch (fan-made, unofficial) |
| `tinywesteros` | an imagined world | Westeros and Essos as one toy-scale diorama, north up, with a clean rectangular frame |

A front page lists the worlds, the cities people are funding next, and links the source.

## This repository is public

Nothing about where or how the site is deployed belongs in a tracked file: no domain, host, IP,
server path, hosting-panel ids, analytics host or site id, payment links, and of course no keys.
All of that lives in the gitignored `deploy/.env` (template: `deploy/.env.example`) and in the
hosting panel's own env vars. Docs and examples use `example.com`. Check `git diff --cached` for
such strings before every commit.

## Layout

```
tinyworlds/
├── tinyworlds-pipeline/   # TypeScript ESM CLI: open data → isometric pixel-art tiles + indexes
├── tinyworlds-frontend/   # Next.js 16 static export: the map viewer (one build per world), the front page, `/admin/` and `/me/`
├── tinyworlds-api/        # NestJS + GraphQL + Prisma: donations, per-city funding milestones, the donation funnel (admins), benefactors and donors' own page (`/me/`)
├── tinyworlds-videos/     # HyperFrames: the front page's card loops and hero, city flyovers, the showcase film, a tour of tinywesteros
├── deploy/                # nginx config, deploy script, .env.example
├── dev.sh                 # tmux launcher
└── CLAUDE.md / README.md
```

Each sub-project has its own `CLAUDE.md`.

## How the pieces fit

- **The maps are static.** Tiles and JSON indexes are generated offline by the pipeline and
  served as files; the viewer needs nothing else to show a city.
- **The API exists only for donations.** Each proposed city is built when donations for it reach
  its goal (US$30); what comes in above the goal pays for servers and upkeep, and the most
  funded cities are built first. The Donate dialog and the front page read `cityMilestones` (the
  ranking) and start a Stripe Checkout through `createDonationCheckout` for the city and amount
  the donor chose; a Stripe webhook records what was paid. If
  the API is unreachable the viewer falls back to static payment links, so donating never
  depends on it.
- **The funnel is the site's own.** Every page says to the API that a visit opened it, and
  then which steps towards a donation that visit took (the donate sign, the checkout, giving
  up); a visit is a tab's stay, named by an id made up in the browser and kept nowhere else
  (no cookie, no address). That gives the donation funnel and each city's count of visits,
  which admins read at `/admin/` (part of the front page's build). Admins sign in through a
  link sent by email; who they are is the API's `ADMIN_EMAILS`, never a tracked file.
- **Donors and benefactors.** A donor is an email address Stripe gave at checkout: no
  password, no account made by hand. A donor who signs in (a link or a 6-digit code sent by email,
  `purpose: "donor"`) reads their own page, "Your cities" at `/me/` of the front page's build:
  what they gave, the badges they earned (founding number, first stone, keystone) and whether
  they are named. Each city's public benefactors (`cityBenefactors`: founders, then benefactors
  by amount, one stone per US$1) are shown on a sign from the front page and from About in a map; a built
  city, which the Donate sign does not offer, reaches Donate only through that sign. Names are the donor's choice, per city; admins can hide one on `/admin/`. Emails never
  appear in the API's answers, and no answer says whether an address has donated.
- **The front page moves.** Its hero and each world's card play a short silent loop made by
  `tinyworlds-videos` from the world's own tiles, over a still; the loops are the front page's
  own files, so nothing but its build needs deploying for them.
- **Google's tags wait for consent.** Google Tag Manager (and the Google Analytics in it) is the
  one thing on the site that sets cookies: visitors in Europe are asked first, and nothing from
  Google loads before they say yes (`tinyworlds-frontend/CLAUDE.md`, Analytics).
- **The interface follows the visitor's language** (en-US, pt-BR, es-ES), whatever the city.
  City data (street and place names) stays in the city's own language.

### Deviations from the global stack (deliberate)

- **The pipeline is a CLI, not a BullMQ worker.** It follows the worker conventions that apply
  (TypeScript ESM, Commander.js entry point, swappable data-source providers) but has no queue.
- **The frontend is a static export** (`output: "export"`), one build per world under
  `/<world>` plus one for the front page. No server components fetch at request time; Apollo
  Client is used only where the API is (the Donate dialog, the front page's milestones).
- **No accounts for visitors.** What the site calls for them is public and throttled. Auth
  exists for admins and for donors (who sign in to see the cities they helped build), and
  without passwords: a sign-in link or its code by email, then a JWT in local storage
  (`tinyworlds-api/CLAUDE.md`). Signing in is REST, as the global stack has it.
- **Funnel steps go out with plain `fetch`**, not Apollo Client: every page sends one, and
  Apollo is only downloaded when the donate sign or the admin page asks for it.

## Adding a world

1. Pipeline: `tinyworlds-pipeline/src/cities/<id>.ts` (see that project's `CLAUDE.md`), then
   `npm run all -- --city <id>` and `npm run cli -- --city <id> card`.
2. Viewer: `tinyworlds-frontend/src/worlds/<id>.ts` and its registry entry.
3. API: mark the city `BUILT` with its `worldId` (see `tinyworlds-api/CLAUDE.md`).
4. Videos: `npm run plates -- <id> && npm run loops -- <id>` in `tinyworlds-videos` gives the world its
   card loop on the front page (`tinyworlds-frontend/public/loops/<id>.mp4`); without one its
   card simply stays still.
5. `deploy/deploy.sh check` (every world in the registry has its data, card, pipeline city and
   docs, this one included), then `deploy/deploy.sh <id>` and `deploy/deploy.sh home`.

The id is `tiny` + a short city code; it is the pipeline's `--city`, the viewer's
`NEXT_PUBLIC_WORLD`, the data folder and the URL path.

## Data contract (pipeline → viewer)

The pipeline writes everything a viewer needs into `tinyworlds-frontend/public/data/<world>/`
(gitignored, reproducible). In production the same folder is served at `/<world>/data/`.

```
data/<world>/
├── manifest.json            # projection, pyramid, tile bitsets
├── tiles/{z}/{tx}_{ty}.webp # lossless WebP, binary alpha (transparent = off the map)
├── overview.webp            # whole map, small: the minimap
├── places.json              # search index
├── hoods.json               # outlines of the city's areas (may be empty)
├── life.json                # ferry routes and flights for the animated layer
├── sights.json              # buildings that light up under the pointer (worlds with sights)
├── sights/<hash>.webp       # each of them drawn on its own, nothing in front of it
└── sights.<locale>.json     # their Wikipedia openings: en-US, pt-BR, es-ES
```

### Map space and projection

Map space is pixels at native resolution (level 0); x grows right, y grows down. Geodata in the
JSON files stays in lon/lat and the viewer projects it with `manifest.geo`:

```
east  = (lon - lon0) · π/180 · R · cos(lat0)        R = 6371008.8
north = (lat - lat0) · π/180 · R
p = east·sin β + north·cos β        // metres "uptown" (along the grid's main axis)
q = east·cos β − north·sin β        // metres crosstown
X = (p + q) · k
Y = (q − p) · k/2 − h · kz          // h = metres above ground
```

β is the bearing of the city's street grid, so its streets run at exact 2:1 pixel slopes. True
north points `manifest.northDeg` clockwise from screen-up.

### manifest.json

```ts
interface Manifest {
  name: string;                 // the world id: "tinynyc"
  build: string;                // the render's cache-busting id: append as ?v= to tiles, overview
  indexes?: string;             // the indexes' (places, hoods, life, sights, their texts and
                                // pictures): append as ?v= to those; absent: use `build`. A hash
                                // of their contents, written by the pipeline's index and wiki
  tileSize: number;             // 512
  origin: { x: number; y: number };   // map-px position of tile (z, 0, 0)'s top-left, all levels
  levels: {
    z: number;                  // 0 = native; level z is downsampled by 2^z
    cols: number; rows: number;
    tiles: string;              // base64 bitset, row-major, bit (tx + ty·cols), LSB-first: 1 = file exists
  }[];
  bounds: { minX: number; minY: number; maxX: number; maxY: number }; // content bounds, map px
  start: { lon: number; lat: number; scale: number };                 // first view
  maxScale: number;             // deepest zoom, screen px per map px
  northDeg: number;
  geo: { lon0: number; lat0: number; betaDeg: number; k: number; kz: number };
  overview: { src: string; width: number; height: number };           // image spans `bounds`
  attribution: string[];        // shown as they are, in every interface language
}
```

Tile `(z, tx, ty)` covers map px `[origin.x + tx·T·2^z, origin.x + (tx+1)·T·2^z)` horizontally and
likewise vertically (`T = tileSize`). Missing tiles are off the map: the viewer leaves the page
background showing.

### places.json

```ts
type Place = {
  n: string;                    // name
  t: "borough" | "hood" | "landmark" | "park" | "bridge" | "museum" | "station" | "street" | "place";
  lon: number; lat: number;
  b?: string;                   // context line: borough, zone, …
  r: number;                    // rank, higher first on ties
  s?: number;                   // suggested scale when flying there
};
// file: { places: Place[] }
```

`borough` is whatever the city's large divisions are (boroughs in New York; zones and planning
sub-sectors in Ribeirão Preto); the viewer labels the types per world.

### hoods.json

```ts
// file: { hoods: { name: string; borough: string; lon: number; lat: number; rings: number[][] }[] }
// rings: flat [lon0, lat0, lon1, lat1, ...] per ring, simplified
```

### life.json

```ts
// file: {
//   ferries: { name: string; path: number[] }[];   // flat [lon, lat, ...]; a boat sails it there and back
//   flights?: {
//     kind: "helicopter" | "plane";
//     path: number[];      // flat [lon, lat, metresAboveGround, ...]
//     loop: boolean;       // a closed circuit flown forever, or start → end repeated after `pause`
//     speed?: number;      // ground metres per second
//     pause?: number;      // seconds
//   }[];
// }
```

Optional for the viewer: without it the map is simply still.

### sights.json, `sights.<locale>.json`

The structures found in the search (buildings, stadiums, the Statue of Liberty, bridges), each
outlined as the map draws it, and what Wikipedia says of them. Only for a world that has them
(the pipeline's `sights` city field, the viewer's `World.sights`).

```ts
// sights.json: { sights: {
//   id: string;            // "b<seed>", "bridge:<name>", "statue:<i>"
//   n: string; t: PlaceType | "building"; b?: string;   // name, type, context line
//   lon: number; lat: number;                           // where its article is looked up
//   rings: number[][];     // the outline, flat MAP PX rings, even-odd: it includes height, so
//                          // it is screen geometry, not geodata (the one exception to lon/lat)
//   front: number;         // largest ground y of its footprints: the nearer the viewer, the larger
//   anchor: [number, number];  // where its sign hangs (the outline's top), map px
//   sprite?: { src: string; x: number; y: number; w: number; h: number };
//                          // its picture: "sights/<hash>.webp", lossless, transparent but for
//                          // the structure, drawn as the tiles draw it (shadows and all) with
//                          // nothing in front of it; x, y, w, h place it in map px
// }[] }
// sights.<locale>.json: { [id]: { title: string; url: string; text: string; lang: string } }
//   text: the article's opening (≤ 220 characters); lang: the article's own language, "en" where
//   the visitor's has none
```

Optional for the viewer: without them nothing lights up; without a sight's picture it still
lights up, as far as the map shows it.

## API contract (viewer ↔ API)

GraphQL at `/api/graphql` (same origin in production):

```graphql
enum CityStatus { PROPOSED FUNDED BUILDING BUILT }
type CityMilestone { id: ID! slug: String! name: String! raisedCents: Int! goalCents: Int! donations: Int! status: CityStatus! worldId: String }
type Query {
  health: String!
  cityMilestones: [CityMilestone!]!
  cityBenefactors(input: CityBenefactorsInput!): CityBenefactors   # public; null for an unknown or hidden city
}
input CityBenefactorsInput { slug: String  world: String }          # one of the two
input CreateDonationCheckoutInput { city: String  amountCents: Int  world: String!  locale: String!  returnUrl: String!  visitId: ID  benefactorName: String }
type DonationCheckout { url: String! }
enum FunnelStep { VISIT DONATE_OPENED CHECKOUT_STARTED CHECKOUT_CANCELLED }
input TrackFunnelStepInput { visitId: ID!  step: FunnelStep!  world: String!  locale: String }
type Mutation {
  createDonationCheckout(input: CreateDonationCheckoutInput!): DonationCheckout!
  trackFunnelStep(input: TrackFunnelStepInput!): Boolean!
}
# donors only (Authorization: Bearer <a donor's session>):
#   query    myGiving: MyGiving!                         # their cities, stones, badges, listing
#   mutation setListing(input: { city: String!, listed: Boolean! }): Boolean!
#   mutation setDisplayName(input: { name: String! }): String!   # answers the cleaned name
# admins only (Authorization: Bearer <an admin's session>):
#   me, donationFunnel
#   query    benefactorNames: [BenefactorName!]!         # newest listed gift first, at most 100
#   mutation setNameHidden(input: { donorId: ID!, hidden: Boolean! }): Boolean!
```

`amountCents` (100 to 1,000,000) fixes the amount; without it the donor chooses on Stripe's page
(from US$1). `visitId` is the tab's visit (a UUID from session storage); `world` is a world's id
or `"home"`. `benefactorName` (1 to 40 characters, cleaned by the API) asks to be named on the
city's benefactors for this gift; without it the gift is counted and not listed. REST: `POST /api/stripe/webhook`, and signing in, for admins and donors alike:
`POST /api/auth/magic-link { email, returnUrl, locale?, purpose? }` (always `202`), then
`POST /api/auth/verify` with `{ token }` or `{ email, code, purpose? }`, answered
`{ accessToken, expiresAt, admin | donor: { id, email } }`. `purpose` is `"admin"` (the default)
or `"donor"`; a session of one kind is `FORBIDDEN` on the other's queries. When the contract
grows, deploy the API before the viewers: an older API refuses a checkout that carries a field
it does not know, and the site then falls back to its payment link. Details in
`tinyworlds-api/CLAUDE.md`.

## Running and deploying

- `./dev.sh [world]` opens tmux with the viewer's dev server, the API and a pipeline shell.
- The pipeline is run by hand (`npm run all -- --city <id>` in `tinyworlds-pipeline`).
- `deploy/deploy.sh <world | home>` builds a viewer and rsyncs it (and the world's data) to the
  web server; `deploy/deploy.sh all [--parallel[=N] | --serial] [--no-data]` checks and builds
  every world in the viewer's registry and the front page, and uploads only if all of them
  built. The API is a container built from `tinyworlds-api/Dockerfile`. See `deploy/README.md`.

## Conventions

- npm, Node 22, TypeScript strict, ESLint + Prettier in every sub-project.
- Raw downloads and generated tiles are never committed (`tinyworlds-pipeline/data/`,
  `tinyworlds-frontend/public/data/`). The share cards in `tinyworlds-frontend/public/og/` and
  the front page's loops in `tinyworlds-frontend/public/loops/` are, and so is each film's music
  bed (`tinyworlds-videos/*/assets/music/`: a film is timed to it); the videos' plates, takes,
  sound effects and renders are not.
- Every picture of a map, still or moving, is cut from the real tiles or filmed from the real
  viewer (`tinyworlds-videos`): nothing is redrawn for a card, a loop or a film.
- Attribution is part of the product: the About panel credits each world's data sources
  (`manifest.attribution`).
- No hard-coded interface strings in the viewer: everything goes through its i18n dictionaries
  in the three languages.
